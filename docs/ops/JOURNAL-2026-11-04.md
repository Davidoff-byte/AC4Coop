## 10. The local two-instance question, settled

Goal: two game copies on one PC, no second machine. Every attempt hit a different wall.

| attempt | wall | evidence |
|---|---|---|
| same Steam exe, second copy | **game mutex** `scimitar_mutex_ac4bf_61979` | string in `AC4BFSP.exe`; the plugin already renames it with an IAT hook on `CreateMutexW` |
| …with the mutex renamed | **Steam**: `SteamAPI_RestartAppIfNecessary` returns true, the new process relaunches the running copy and exits | `steam_api.dll` export; observed — launching copy 2 brings copy 1's window forward |
| repack copy (no Steam at all) | different binary: `54CA73AF`, 45,123,288 B vs `BC11AD79`, 45,056,040 B — every hardcoded offset wrong | `0xC0000005` at `0x0060AEC7` about 10 s after the hooks install |
| Steam exe dropped into the repack | the repack's Uplay emulator lacks `UPLAY_USER_IsOwned` | *Entry Point Not Found* dialog |

**Conclusion:** two Steam copies on one licence is blocked by Steam, not by the game. The only
Steam-free local copy is the repack, which needs a build port. Kamzik's reference build carries the
same mutex hook and no Steam handling at all — his verified result is *two machines over Radmin*,
which we already have.

## 11. Build-to-build relocation — what works, what does not

| tool | method | result on `54CA73AF` |
|---|---|---|
| `sig_locate.py` | raw byte signatures | 35/53 — **invalid result** |
| `sig_exact.py` + `pe.py` | same, with correct PE section mapping | **36/101, 22 unique** |
| `fn_match.py` | normalised function matching, size-filtered | unusable |

The first two runs were invalid because `.text` sits at RVA `0x1000` but file offset `0x400`, so
every signature was read 0xC00 bytes early. Fixed and documented; corrected map in
`docs/evidence/sig_map_v3.json`.

`fn_match.py` fails for a structural reason: `GetWorld` is a 7-instruction, 20-byte getter and
`GetPlayer` is a 3-instruction thunk. Shape matching returns five "perfect" candidates and proves
nothing. Short functions must be identified semantically — by callers and the data they touch —
which is manual analysis. **65 of 101 sites remain unresolved.**

## 12. INCIDENT — 37 GB of extracted Unity assets destroyed (self-inflicted)

**What was lost.** `C:\Users\Administrator\acu-movement-rs` went from
**47,541 MB / 3,299,359 files** to **6,361 MB / 458,338 files**.

```
assets_all\ACU   43,072 MB -> 5,943 MB   ~37 GB of the extracted DataPC_ACU_* tree
target\          build dir -> gone       (rebuildable)
src\             INTACT — main.rs, movement.rs, navigation.rs, node.rs, anim.rs, human.rs,
                 action_bounds.rs, action_data.rs, lib.rs, bin\
```

**Cause, exactly.** A background `robocopy /MOVE` (C: → D:) was still alive when a "restore"
(D: → C:) was started. The restore copied back and then deleted the D: copy. The original job was
still running; its cleanup step — `Remove-Item $src` on what it took for leftovers — then deleted
the C: tree that had just been restored. Two writers on one tree, both deleting.

**Why the filesystem cannot undo it.** No shadow copies, no restore points, recycle bin empty:
`robocopy` and `Remove-Item` delete permanently.

**Why it is not fatal.** `assets_all` was derived data. The 43 source forge files (30,558 MB) are
still in the Unity install (`…\games\Assassin's Creed Unity`); re-extraction with
ACExplorer/AnvilToolkit reproduces the tree. The authored source survived untouched.

**Rules added.**

1. One mover per tree. Check `Get-Process robocopy` before any move or restore.
2. Never start a reverse move while a forward move is alive.
3. Prefer `/MOV` to `/MOVE` when the destination may later be deleted — `/MOVE`'s cleanup is
   irreversible.
4. Verify with file **counts**, not sizes; the tree still looked "present" at 6.3 GB.
