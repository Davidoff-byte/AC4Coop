## S0.1 - how a ship's rigid body gets into the physics world (keystone K-a)
Static chain (decompiled):
- `sub_747D20` = RigidBodyComponent "added to world" (base of ShipPhysicComponent vt 0x0272D378 slot 87 `sub_1C66930`;
  slot 88 `sub_1C51870` -> `sub_738B50` is the removal twin). Gates: component+4 & 0x4000000, body = *(comp+0xA0+0x74)
  non-null, byte comp+341, motion bits (comp+272 & 0xC) vs body in-world. Under the world physics lock
  (`sub_8264E0` / `sub_826360` on *(*(World+0x7F4)+0x120)) it calls `sub_5BE3C0(comp, comp+0xA0, World)`.
- `sub_5BE3C0` (cdecl): body+0xC = comp (user data); `sub_636E90(comp+0xA0+0x64, body, 1)` binds the collision filter;
  `sub_5B4070(rb, entity matrix)` writes the body transform; `sub_5B4000(rb, World)` -> `sub_44BE50` ("TtAddRigidBody").
- `sub_44BE50`: in the threaded branch (byte_27472CF && rb+0x60 <= 1 && sub_590800()) it queues through `sub_428320`;
  otherwise, when the body is not in a world (`body+8 == 0`), `sub_C39FB0(body, 1)` adds it.
- `sub_1588540` is NOT a physics-manager getter (SHIP-PHYSICS.md §5): it returns *(this+0x74) = the hkpRigidBody of a
  RigidBody struct.
Our ghost (DuplicateShip, phase1.cpp:4020-4047) installs the constructed body BEFORE World::AddEntity, so the engine's own
handler runs with a body; MODLOG.md:2518 reports m_world=0 afterwards, so one of the gates above stops it. Which one is a
runtime fact: read comp+4, comp+341, comp+272, rb+0x60, body+8 on the ghost after AddEntity (S4 probe).
Verdict: **path found (static)**; the failing gate is the open runtime question.
